# Cesium 大批量点位渲染优化

## 模拟场景

本示例模拟的是低空安全、城市监控、物联网设备上图一类业务：地图上需要同时展示几千、几万，甚至十万级点位。每个点代表一个监测对象，例如无人机、传感器、告警设备或巡检目标，并携带 `normal`、`warning`、`danger` 等状态。

这类场景的主要特点是：

- 点位数量大，但单个点的几何形态简单。
- 用户经常缩放、平移地图，需要快速看到全局密度和局部细节。
- 点位状态可能频繁更新，但不一定需要每一帧连续渲染。
- 远距离观察时，完整绘制所有点的业务价值不高，反而容易造成卡顿。

因此，这个示例不是追求“把所有点无差别塞进地图”，而是演示不同渲染策略的成本差异，以及如何按观察距离和业务优先级减少无效绘制。

## 常见性能瓶颈

### 大量 Entity 的管理成本

`Entity` API 易用、表达能力强，适合中小规模对象或需要复杂属性、时间动态、拾取交互的对象。但如果每个点都创建一个 `Entity`，数量达到几万级后，Cesium 需要维护大量高级对象、属性系统和可视化器调度，CPU 管理成本会明显上升。

在本示例中，`Entity` 模式被作为基准模式，用来对比它和底层集合类之间的差异。

### 一次性创建导致主线程阻塞

如果一次性创建几万或十万个点，浏览器主线程会长时间执行 JavaScript，页面会出现明显卡顿，甚至短暂无响应。

这个问题不一定来自 GPU 绘制，很多时候是对象创建、经纬度转换、集合插入、样式初始化这些 CPU 工作集中爆发造成的。

### 高 DPI 屏幕渲染压力

在高分屏上，Cesium 的 WebGL canvas 实际绘制像素可能远高于 CSS 尺寸。点位很多时，像素填充和后处理成本会被放大。

### 远距离无效绘制

当相机高度很高时，屏幕上很多点会挤在同一小片区域。继续绘制所有点并不能提供更多有效信息，却会消耗 CPU 和 GPU 资源。

## 本示例中的优化方法

### 1. 用 PointPrimitiveCollection 渲染简单点位

对于只是展示位置和状态颜色的点位，优先使用 `PointPrimitiveCollection`。它比 `Entity` 更贴近 Cesium 底层渲染模型，减少了高级对象管理成本，适合几万级简单点位展示。

适用场景：

- 点位只需要颜色、大小、高度等简单样式。
- 不需要复杂时间动态属性。
- 不需要每个点挂载大量业务字段。

示例中的默认策略就是 `PointPrimitiveCollection + 分批加载 + 显式渲染`。

### 2. 用 BillboardCollection 表达图标状态

当点位需要更明确的业务图标，例如告警、设备类型、飞行器状态时，可以使用 `BillboardCollection`。

它的表达力比纯点更强，但纹理、透明像素和屏幕填充成本也更高。因此它适合中等规模图标展示，或者配合视距过滤、聚合、分层显示使用。

### 3. 保留 Entity 作为对照和特殊对象

`Entity` 并不是不能用，而是不适合无差别承载所有海量点。更合理的方式是：

- 海量普通点使用 `PointPrimitiveCollection`。
- 少量重点对象、选中对象、动态对象使用 `Entity`。
- 交互详情通过选中后临时创建 Entity 或弹窗来表达。

### 4. 分批加载，避免长任务阻塞

示例中通过 `requestAnimationFrame` 分批插入点位。这样可以把一次长任务拆成多个小任务，让浏览器有机会处理输入、布局和渲染。

这不会减少总计算量，但能显著改善页面“卡死”的体感。对于十万级点位，分批加载比一次性加载更适合作为默认策略。

### 5. 根据相机高度做视距抽样

示例中根据 `viewer.camera.positionCartographic.height` 判断相机高度：

- 近距离：渲染全部点，保证细节。
- 中距离：按比例抽样，保留空间分布趋势。
- 远距离：进一步减少点数，只展示整体密度。

这种策略本质是“按视图重要性裁剪数据”。它适合全局概览场景，也方便后续替换成更正式的方案，例如网格聚合、四叉树、矢量瓦片或 3D Tiles。

### 6. 启用 requestRenderMode 显式渲染

当场景不是每一帧都变化时，可以开启 `requestRenderMode`。数据变化、相机变化或控件操作后再调用 `viewer.scene.requestRender()`。

这样可以减少空闲状态下的连续渲染开销，尤其适合监控面板、态势地图、静态点位分布图。

注意：如果页面里有连续动画、动态材质或实时轨迹，则需要谨慎使用显式渲染，避免画面不更新。

### 7. 降低 resolutionScale

示例提供了分辨率缩放开关。降低 `viewer.resolutionScale` 可以减少 WebGL canvas 实际绘制像素，在高 DPI 屏幕或弱性能设备上比较有效。

代价是画面会略微变糊。实际项目中可以按设备性能、点位数量或用户设置动态调整。

### 8. 避免把大数组放进深层响应式

海量点位数据只保留为普通数组，不放进 Vue 的深层响应式系统。Vue 只管理控制项和统计信息。

这样可以避免大量点对象被代理，减少内存和响应式追踪成本。

### 9. 做好生命周期清理

页面卸载时需要清理：

- 当前渲染任务。
- Cesium primitive 集合。
- 相机事件监听。
- `postRender` 帧率统计监听。
- 延迟重绘定时器。

否则切换页面后可能出现内存残留、重复渲染或控制台报错。

## 策略选择建议

| 场景 | 推荐方案 |
| --- | --- |
| 几千个点，重交互、重业务属性 | `Entity` 可以接受 |
| 几万级普通状态点 | `PointPrimitiveCollection` |
| 几万级图标点 | `BillboardCollection` 配合抽样或聚合 |
| 十万级全局概览 | `PointPrimitiveCollection` + 视距抽样 |
| 百万级及以上 | Worker 聚合、矢量瓦片、3D Tiles 或服务端分层 |

## 后续可扩展方向

当前示例是前端单页模拟，适合验证思路和对比策略。真实项目中可以继续扩展：

- 使用 Web Worker 生成点位、做网格聚合或空间索引。
- 按瓦片或行政区分片加载数据。
- 使用四叉树按视窗范围筛选点位。
- 远距离展示聚合热力或数量标记，近距离展示真实点。
- 将超大规模静态点位预处理为 3D Tiles 或矢量瓦片。
- 对实时数据做增量更新，而不是每次全量重建集合。
